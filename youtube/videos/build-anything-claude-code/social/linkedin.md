## POST 1 - The story

Most people think building an app means learning to code first.

It does not anymore, and I wanted to prove it in the least impressive way I could.

So I made a video for the person who has never opened a terminal in their life. No coding background, no idea what any of this is. That exact person.

I kept running into them. People would ask me about Claude Code, get excited, and then get stuck on the terminal and quietly give up.

So we start from nothing.

Claude Code is a tool that lives in your terminal, and you talk to it in plain English. You tell it what you want and it writes the code and builds it for you.

Installing it is one command. One line on Mac, one on Windows.

Then you make a free Claude account, log in, and type claude to start. That is the whole setup, about two minutes.

Then we build something real together. A countdown timer app.

I typed what I wanted in plain sentences. It built the whole thing. When the timer hits zero you get confetti. About ten minutes, and I did not write a line of code by hand.

I also show the parts that make it feel safe when you are brand new.

Plan Mode, which is Shift+Tab, shows you the plan before it touches anything. Escape cancels whatever it is doing if you change your mind. Nothing happens without you saying yes.

And slash commands give you the built in shortcuts, so there is nothing to memorize.

The whole point is that the barrier most people are still waiting on is already gone.

You do not need to be technical. You need to be able to describe what you want.

## POST 2 - The tactic (no link)

The single most useful thing I show beginners in Claude Code is Shift+Tab.

It sounds like a small keyboard tip. It is actually the thing that makes people stop being scared of the tool.

Shift+Tab turns on Plan Mode.

In Plan Mode, Claude does not do anything. It writes out what it intends to do, step by step, and then waits.

You read the plan. If it is wrong, you say so. If you do not want any of it, you press Escape and nothing ever happened.

That is it. That is the whole tactic.

And I think it matters far beyond a first app, because it changes the shape of how you work with AI on anything.

The default way people use these tools is to ask, get a result, and then figure out whether the result was right. You are checking work after the fact, which is the slowest possible place to catch a mistake.

Plan Mode moves that check to the front. You are approving an approach instead of auditing an output.

I use the same idea outside the terminal now. Before I let anything run on my real work, I ask it what it is about to do and why.

Nine times out of ten it is fine and I say go. The tenth time it was about to do something completely reasonable that I did not want, and I caught it in ten seconds instead of twenty minutes.

The honest version of this is that AI is going to be wrong sometimes. Never expect a hundred percent. Plan Mode is just the cheapest place to find out.

If you use these tools every day, where in your process are you checking the work? Before or after?

## POST 3 - The honest take (soft link)

The app I build in that beginner video is a countdown timer, and I know that is not impressive.

I want to be upfront about that, because I think the overselling in this space is doing real damage.

It is a small app. It took about ten minutes. When the timer hits zero you get confetti. That is the whole thing.

It is not meant to impress you. It is meant to show you the door is open.

And here is what I am careful not to claim. Building that timer did not make anyone a developer.

You will not understand what the code does. You will not know why it made the choices it made. The first time something breaks, you will be asking Claude to fix it rather than fixing it yourself.

That is a real limitation and it does not go away just because the demo went smoothly.

What actually changed is the starting line. The thing that used to stop people was not talent, it was the first hour. Installing things. The terminal. Not knowing the words.

That hour is gone now, and that is genuinely a big deal.

So the honest framing is this. You are not skipping the learning. You are skipping the part that made people quit before the learning started.

Pick something small and just do it. The first one is supposed to be small.

Then when it breaks, and it will, you learn the next piece because you actually need it. That order works a lot better than reading a book first.

What is the small thing you would build if the first hour was already handled?
